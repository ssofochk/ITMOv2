# Reflection — practice_04

## 1. Что помогло

- **`AGENTS.md` как единый источник правил**: в нём были зафиксированы требования к работе, запрет на ослабление проверок и обязательный TDD-подход.
- **Skill `test-driven-development` и `writing-good-tests.md`** задали понятный цикл: сначала failing test, затем минимальная реализация, затем повторная проверка до GREEN.
- **Context7** помог найти документацию FastMCP и подтвердить нужный API для stdio-сервера, `@mcp.tool` и `mcp.run()`, вместо того чтобы полагаться на память модели.
- **Unit-тесты оказались главным источником правды.** До добавления новых тестов поведение `practice-checker` выглядело рабочим, но тесты выявили две реальные ошибки: неправильный `checked_root` и `ok: true` при отсутствующих обязательных артефактах.
- **Автоматический hook** дал наблюдаемый цикл FAIL → PASS: после контролируемого изменения runner вернул ошибку, а после исправления автоматически прошёл.
- **Отдельный `.venv` для MCP** позволил изолировать FastMCP от системного Python и сделать окружение запуска сервера предсказуемым.
- **Ручной JSON-RPC вызов** был полезен как промежуточный диагностический шаг: он позволил проверить исправленную бизнес-логику MCP до восстановления интеграции с OpenCode. Финальным подтверждением всё равно стали реальные вызовы MCP tool через OpenCode.

## 2. Что мешало

- **Корпоративная модель VseLLM перестала принимать запросы**: прямой запрос к gateway вернул HTTP 402, поэтому основной корпоративный LLM пришлось заменить.
- **Локальная `qwen3.5:4b` работала на 100% GPU, но оказалась слишком медленной для agentic workflow** и не всегда корректно пользовалась доступными tools.
- **Nemotron 3 Ultra Free периодически получал `503 Service temporarily overloaded` от Nvidia**, из-за чего приходилось ждать retry и иногда повторно проверять состояние работы.
- Первый вариант MCP содержал **самописную реализацию JSON-RPC/MCP transport**. Unit-тесты бизнес-логики при этом могли проходить, но OpenCode не мог нормально удержать соединение с сервером.
- В одной из версий `server.py` сервер создавался, но **`server.run()` не вызывался**, поэтому процесс фактически не начинал обслуживать MCP.
- В WSL изначально **не был установлен пакет `python3.14-venv`**, а FastMCP отсутствовал в системном Python. Для сервера пришлось отдельно подготовить `.venv`.
- После создания `.venv` OpenCode всё ещё запускал MCP через системный `python3`, поэтому сервер падал с `Connection closed`. Команду запуска пришлось явно переключить на Python из `.venv`.
- В одном месте агент вместо прямого MCP tool call сам запустил **вложенный `opencode run --model ollama/qwen3.5:4b`**, что усложнило цепочку исполнения и не соответствовало требуемому сценарию проверки.

## 3. Где потребовалось моё вмешательство

- Я зафиксировала, что **TDD обязателен**, а проверки нельзя ослаблять ради зелёного результата.
- После первого реального вызова `check_submission` я заметила, что переданный `practices/practice_04` ошибочно воспринимается как корень репозитория. Пришлось явно потребовать поиск настоящего repo root через `.git` или `opencode.json`.
- Я отдельно указала, что **`ok` должен быть `false`, если отсутствует хотя бы один обязательный артефакт**, потому что первая версия возвращала `ok: true` даже при неполной сдаче.
- Я заметила отсутствие `server.run()` в `server.py` и потребовала исправить запуск сервера.
- После проблем с самописным transport я потребовала использовать **FastMCP вместо ручной реализации протокола**, тем более что документация FastMCP уже была найдена через Context7.
- Я запретила вложенные `opencode run`, прямые JSON-RPC вызовы и другие обходные пути для финальной проверки, чтобы подтверждение происходило именно через MCP tool текущей OpenCode-сессии.
- Я вручную исправила command в `opencode.json`, чтобы MCP запускался через Python из `.venv`, а не через системный интерпретатор.
- После полного перезапуска OpenCode я проверила два настоящих вызова `practice-checker`: существующий путь вернул `ok: true`, а несуществующий — `ok: false` с понятной ошибкой.

## 4. Что я вынесла из работы

- **Сам факт подключения инструмента не означает, что его результат правильный.** Первый MCP tool call технически сработал, но вернул неправильный `checked_root` и некорректный `ok`.
- **Узкие и проверяемые поручения работают лучше общих.** Формулировка «сначала создай тест, который воспроизводит текущую ошибку» дала намного более предсказуемый результат, чем абстрактное «исправь MCP».
- **Автоматические проверки и реальные tool calls надёжнее текстовых утверждений модели.** Несколько раз модель сообщала об успешном состоянии, хотя только тесты или реальный вызов показывали фактическую проблему.
- **Человеческая проверка особенно нужна там, где технически всё выглядит зелёным, но семантика неверная.** Старые тесты проходили, потому что фактически закрепляли ошибочное поведение. Только новые проверки выявили расхождение со спецификацией.
- **Окружение исполнения является частью агентной системы.** Наличие правильного кода MCP недостаточно, если OpenCode запускает его неправильным Python или без нужных зависимостей.
- **В моей сессии OpenCode не восстановил MCP автоматически после завершения процесса**, поэтому для финальной проверки потребовался полный рестарт и новая сессия.
- В итоге наиболее надёжным оказался не сам текст ответа модели, а цепочка наблюдаемых подтверждений: TDD RED → GREEN, hook FAIL → PASS, подключённый MCP и два реальных вызова собственного tool.
