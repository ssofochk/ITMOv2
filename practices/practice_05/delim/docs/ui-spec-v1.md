# Делим — UI спецификация v1

Версия: v1
Команда: UI (независимая от команды бизнес‑логики)

1. Цель и сценарии

Цель: предоставить понятный, быстрый и доступный интерфейс для учёта совместных расходов и расчётов между участниками с локальным сохранением данных.

Основные пользовательские сценарии:
- Добавление участников компании.
- Добавление расхода: название, сумма в рублях, плательщик, перечень участников, между кем распределяется трата.
- Просмотр истории расходов и удаление ошибочных записей.
- Просмотр личных балансов по участникам.
- Получение списка рекомендуемых переводов «кто кому сколько должен».
- Сохранение данных между перезагрузками страницы.

2. Структура основного экрана

- Верхняя панель: название «Делим», переключатели вкладок: «Участники», «Расходы», «Балансы», «Переводы»; кнопка «Очистить данные» (с подтверждением).
- Основная область — контент активной вкладки.
- Нижняя вспомогательная панель (или боковая на десктопах): краткие подсказки по вводу, дисклеймер первой версии.

3. Участники: создание и отображение

- Секция «Участники»:
  - Поле ввода имени участника, кнопка «Добавить».
  - Список участников: карточки с именем. Для будущих версий допускается аватар, но v1 — имя.
  - Валидация: непустое имя, уникальность внутри счёта (без учёта регистра). Ошибки — inline.
  - Кнопка удаления участника недоступна, если участник встречается в расходах (v1: чтобы не терять историческую целостность). Пояснение UI.

4. Форма добавления расходов

- Секция «Расходы» — форма:
  - Название расхода (строка, обязательное, 1–80 символов).
  - Сумма (десятичное число в рублях, обязательное, > 0; шаг 0.01; локальный формат ввода).
  - Плательщик (выпадающий список среди участников, обязательное).
  - Кого касается расход (мультивыбор участников; минимум один).
  - Способ распределения (v1 — равными долями между выбранными участниками). Будущее: веса/доли — не включаем в v1.
  - Кнопка «Добавить расход».
  - Валидации: все поля обязательны; сумма > 0; минимум один участник выбран; плательщик входит в общий список участников (может, но не обязан входить в список «кто делит»).

5. Выбор плательщика и участников траты

- Плательщик — одиночный выбор из списка участников.
- Участники траты — чекбоксы/теги со множественным выбором. Для длинных списков — поиск по имени.
- Подсказки:
  - Если плательщик не входит в делящихся, интерфейс показывает, что плательщик оплатил за других.
  - Если плательщик входит в делящихся, интерфейс показывает, что часть суммы относится и к нему.

6. Список расходов и удаление записей

- Под формой — список расходов (история):
  - Карточка: название, сумма, плательщик, количество делящихся (с раскрытием имен), дата/время добавления.
  - Кнопка «Удалить» на каждой карточке: удаляет запись без каскадных изменений участников.
  - Подтверждение удаления. После удаления перерасчитываются балансы и переводы.
- Сортировка по времени добавления, самый новый сверху.
- Пустое состояние: текст и кнопка «Добавить первый расход» (фокус переводится на форму).

7. Итоговые балансы и рекомендуемые переводы

- Вкладка «Балансы»:
  - Таблица/список участников с суммарно «сколько потратил», «сколько должен был потратить», «нетто баланс» (положительный — должен получить, отрицательный — должен отдать).
  - Пустое состояние — если нет расходов, показывать нули и подсказку.
- Вкладка «Переводы»:
  - Рекомендованный минимальный набор переводов «кто кому сколько должен» для сведения балансов к нулю (алгоритм — от команды логики).
  - Отображение: список строк «А должен Б — X руб.». Без фактических платежей в v1.

8. Состояния интерфейса

- Пустые данные: информативные пустые состояния во всех вкладках.
- Успешные операции: ненавязчивые тосты/алерты после добавления/удаления.
- Ошибки валидации: inline под полями, доступные для чтения экрана.
- Некорректный ввод:
  - Имя участника пустое или неуникальное — блокировать добавление, показать причину.
  - Сумма <= 0 или нечисловое — блокировать добавление расхода.
  - Не выбран плательщик или ни один участник — блокировать добавление.
- Ошибки хранения: при недоступности localStorage — предупреждение, данные не сохранятся.

9. Адаптивность и доступность

- Адаптивность:
  - Мобильный: вкладки — нижняя панель; формы — вертикальные; списки — компактные.
  - Десктоп: вкладки — верхняя панель; формы — двухколоночные при достаточной ширине; история — таблица/карточки.
  - Контент не «прыгает», минимальная ширина 320px.
- Доступность:
  - Семантическая разметка, заголовки, aria‑метки для интерактивных элементов.
  - Управление с клавиатуры: вкладки, формы, удаление записей.
  - Контраст и видимый фокус.

10. Предполагаемый API взаимодействия UI с логикой

UI ожидает предоставление модулей/функций для работы с данными и расчётами. Формулируем в TS‑терминах без реализации.

Типы данных (ожидания UI):

```
type ParticipantId = string;

interface Participant {
  id: ParticipantId;
  name: string; // уникально в рамках счёта
}

interface Expense {
  id: string;
  title: string;
  amountRub: number; // > 0, точность до копеек
  payerId: ParticipantId;
  involvedIds: ParticipantId[]; // минимум один
  createdAt: string; // ISO8601
}

interface BalanceRow {
  participantId: ParticipantId;
  spentRub: number;
  shouldHaveSpentRub: number;
  netRub: number; // spent - shouldHaveSpent
}

interface TransferSuggestion {
  fromId: ParticipantId;
  toId: ParticipantId;
  amountRub: number; // > 0
}

interface StoreSnapshot {
  participants: Participant[];
  expenses: Expense[];
}
```

Функции (ожидания UI):

- Участники:
  - `addParticipant(name: string): Participant | UIError`
  - `listParticipants(): Participant[]`
  - `canRemoveParticipant(id: ParticipantId): boolean` // false, если участник встречается в расходах
  - `removeParticipant(id: ParticipantId): void | UIError` // v1 UI может не показывать кнопку, если `canRemove=false`
- Расходы:
  - `addExpense(input: { title: string; amountRub: number; payerId: ParticipantId; involvedIds: ParticipantId[] }): Expense | UIError`
  - `listExpenses(): Expense[]`
  - `removeExpense(id: string): void | UIError`
- Расчёты:
  - `computeBalances(snapshot: StoreSnapshot): BalanceRow[] | UIError`
  - `suggestTransfers(balances: BalanceRow[]): TransferSuggestion[] | UIError`
- Хранение:
  - `loadSnapshot(): StoreSnapshot | UIError`
  - `saveSnapshot(snapshot: StoreSnapshot): void | UIError`

Ошибки:

```
interface UIError {
  code: string; // e.g. 'validation', 'conflict', 'storage_unavailable'
  message: string; // для показа пользователю
  details?: unknown; // для логирования
}
```

11. Acceptance criteria (Given / When / Then)

- Добавление участника:
  - Given пустой список участников
  - When пользователь вводит уникальное непустое имя и нажимает «Добавить»
  - Then участник появляется в списке; форма очищается; показывается тост «Участник добавлен».

- Валидация имени:
  - Given список уже содержит «Анна»
  - When пользователь вводит «анна»
  - Then кнопка «Добавить» недоступна, отображается ошибка «Имя должно быть уникальным».

- Добавление расхода:
  - Given есть минимум один участник
  - When заполнены корректные поля (название, сумма > 0, выбран плательщик, отмечены участники) и нажата «Добавить расход»
  - Then запись появляется в истории сверху; показывается тост «Расход добавлен».

- Удаление расхода:
  - Given в истории есть запись
  - When пользователь нажимает «Удалить» и подтверждает
  - Then запись исчезает, балансы/переводы пересчитываются; показывается тост «Расход удалён».

- Просмотр балансов:
  - Given существуют расходы
  - When пользователь открывает вкладку «Балансы»
  - Then отображается таблица с корректными значениями нетто для каждого участника.

- Просмотр переводов:
  - Given балансы содержат положительные и отрицательные значения
  - When пользователь открывает вкладку «Переводы»
  - Then отображается рекомендуемый список переводов, сумма > 0 в рублях.

- Сохранение данных:
  - Given пользователь добавил участников и расходы
  - When перезагружает страницу
  - Then данные восстанавливаются из localStorage.

12. Открытые вопросы и предположения

- Формат округления копеек при делении «поровну» (банковское округление? стратегия распределения остатка копеек).
- Может ли плательщик отсутствовать среди «делящих» в v1 — предполагаем «да».
- Политика удаления участника с историей — предполагаем запрет в v1 (кнопка скрыта), альтернатива — «архивировать»?
- Идентификаторы — строки (UUID) или числовые? UI ожидает строки.
- Порядок минимизации переводов — алгоритм от команды логики; UI готов к списку произвольной длины.
- Лимит участников/расходов в одном счёте — не задан, UI должен масштабироваться.
- Локализация — v1 на русском; поля — одна валюта (рубли, формат РФ).
