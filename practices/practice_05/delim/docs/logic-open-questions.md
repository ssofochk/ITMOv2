# Делим — открытые вопросы и допущения (логика)

Этот документ фиксирует предположения, решения и вопросы, требующие согласования с UI-командой. Он не опирается на UI-спецификацию.

## Принятые допущения

- Имена участников могут повторяться. По UX это может быть неудобно, но логика не навязывает уникальность.
- Плательщик может не быть в списке бенефициаров расхода. Это отражает кейс «оплатил за других».
- Удаление участника, участвовавшего в тратах, запрещено; возможен `archived` для скрытия.
- UUID v4 — формат идентификаторов; сортировка по UUID обеспечивает детерминизм при распределении остатков и взаимозачёте.
- Все суммы храним в копейках `number` (JS). Ограничение по максимуму обсуждается.
- JSON-сериализация без форматирования; версия схемы фиксируется в `schemaVersion`.

## Вопросы к UI-команде

1. Уникальность имён участников:
   - Нужна ли валидация уникальности на UI-уровне, подсказки/автодобавление суффиксов?

2. Поведение при попытке удалить участника «в использовании»:
   - Нужен ли режим «архивации» участника с запретом добавления его в новые расходы? Как отображать архивацию?

3. Плательщик вне `splitAmong`:
   - Должно ли UI по умолчанию включать плательщика в список бенефициаров, или оставлять решение пользователю?

4. Максимальные суммы и формат ввода:
   - Каковы ограничения суммы в интерфейсе (например, до 1 млрд копеек)? Нужно ли предупреждение о переполнении чисел в JS?

5. Обработка дубликатов участников по имени при отображении:
   - Должны ли мы показывать id/метки для различения, или UI обеспечит уникальность визуально?

6. Схема локального хранения:
   - Ключ в `localStorage`, стратегия миграции при обновлении схемы, поведение при повреждённых данных (prompt на сброс?).

7. Ошибки и UX:
   - Формат отображения `LogicError.message`, локализация: UI берёт `code` и мапит на строки?

8. Доп. фичи на будущее:
   - Взвешенное распределение (weights), «доли» вместо равных частей — есть ли в планах?
   - Мультивалютность в будущих версиях?

9. Порядок детерминизации остатков:
   - Нас устраивает сортировка по UUID; UI может ожидать другой порядок (по добавлению/по имени)? Нужно согласовать.

10. Импорт/экспорт:
   - Планируется ли экспорт/импорт состояния пользователем? Если да, уточнить формат и UX предупреждений.

## Примеры UX вопросов с влиянием на логику

- Как UI предотвращает пустые описания расходов: обрезка пробелов, подсветка ошибок.
- Как UI отображает рекомендуемые переводы: группировка по получателю, сортировка.
- Поведение при удалении расхода: подтверждение, восстановление (undo)? Логика готова к идемпотентности delete.

## Критерии согласования

- Уникальность имен — либо обеспечивается UI, либо явный отказ от неё.
- Политика архивации участников — согласовать сценарии и ограничения.
- Ограничение суммы и обработка переполнения — зафиксировать в UI-валидации.
- Ключ `localStorage`, версия схемы и стратегия миграции — согласовать.
