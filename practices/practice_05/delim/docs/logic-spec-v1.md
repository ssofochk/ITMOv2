# Делим — независимая спецификация бизнес-логики (v1)

Версия: 1.0 (только логика). Эта спецификация разработана независимо от UI-спецификации и описывает доменную модель, инварианты и алгоритмы расчёта для приложения «Делим». Реализация и UI на этом этапе не создаются.

## 1. Область и цели

- Один общий счёт, одна валюта (рубли), хранение в `localStorage`.
- Нет внешнего бэкенда, авторизации, банковских интеграций.
- Основные действия: управление участниками, фиксация расходов, перерасчёт балансов, формирование рекомендуемых переводов, удаление ошибочных расходов, загрузка/сохранение состояния.
- Все денежные значения хранятся в целых копейках (integer cents). Потеря копеек недопустима.

## 2. Доменная модель

- Participant — участник общего счёта.
- Expense — расход: сумма, описание, плательщик, список участников, между которыми делится трата (далее — «бенефициары»).
- Balance — чистый баланс участника: `paid_cents − owed_cents`.
- Transfer — рекомендуемый перевод для взаимозачёта: «кто кому сколько».
- ApplicationState — сериализуемое состояние приложения.

## 3. Структуры данных (TypeScript формы)

Примечание: идентификаторы — стабильные строковые UUID (регистр- и формат-зависимость не допускается, валидируем как canonical UUID v4). Поля `createdAt`, `updatedAt` — миллисекунды Unix epoch (number).

```
type UUID = string; // canonical UUID v4

interface Participant {
  id: UUID;
  name: string; // не пустая, trim() применим; уникальность имени не требуется (см. вопросы)
  createdAt: number;
  archived?: boolean; // soft-hide; по умолчанию false
}

interface Expense {
  id: UUID;
  description: string; // не пустая после trim
  amountCents: number; // > 0, целые копейки
  payerId: UUID; // существующий участник
  splitAmong: UUID[]; // непустой список существующих участников (уникальные id)
  createdAt: number;
}

interface Balance {
  participantId: UUID;
  netCents: number; // >0 кредитор, <0 должник, 0 — нейтрально
}

interface Transfer {
  fromId: UUID; // должник
  toId: UUID;   // кредитор
  amountCents: number; // > 0
}

interface ApplicationState {
  schemaVersion: 1; // для будущих миграций
  participants: Participant[];
  expenses: Expense[];
  meta: {
    createdAt: number;
    updatedAt: number;
  };
}

interface LogicError {
  code: string; // см. раздел 7.3
  message: string; // человекочитаемо, локализуется на UI-уровне
  details?: Record<string, unknown>;
}
```

Ограничения и связи:
- `Expense.payerId` должен ссылаться на существующего `Participant.id`.
- `Expense.splitAmong` содержит только существующие `Participant.id`, уникальные, не пустой массив.
- Плательщик может, но не обязан входить в `splitAmong` (см. бизнес-правила).
- Имена участников не гарантируются уникальными; уникальность идентификаторов обязательна.

## 4. Контракты операций (внутренний TS API)

Сигнатуры даны на уровне типов. Реализация отсутствует. Результаты функций используют схему `Either<Result, LogicError>`; конкретная форма может быть `Result<T, E>` или `Promise<Result<T, E>>` в зависимости от интеграции с UI.

### 4.1 Добавление участника

```
function addParticipant(state: ApplicationState, name: string):
  { state: ApplicationState; participant: Participant } | LogicError
```

Правила:
- `name.trim().length > 0` иначе `INVALID_PARTICIPANT_NAME`.
- Генерируется новый `id` (UUID v4), `createdAt = now`, `archived = false`.
- Имена не уникальны по умолчанию; конфликт имени не является ошибкой (см. вопросы к UI).

### 4.2 Удаление участника

```
function removeParticipant(state: ApplicationState, participantId: UUID):
  { state: ApplicationState } | LogicError
```

Правила:
- Разрешено удаление только если участник не фигурирует ни в одном `Expense` как `payerId` или в `splitAmong`.
- При нарушении — `PARTICIPANT_IN_USE`.
- Если не найден — `PARTICIPANT_NOT_FOUND`.
- Альтернатива: `archiveParticipant` (soft delete) — см. вопросы к UI.

### 4.3 Добавление расхода

```
interface AddExpenseInput {
  description: string;
  amountCents: number; // > 0
  payerId: UUID;
  splitAmong: UUID[]; // непустой, уникальные id
}

function addExpense(state: ApplicationState, input: AddExpenseInput):
  { state: ApplicationState; expense: Expense } | LogicError
```

Правила валидации:
- `amountCents > 0` иначе `INVALID_AMOUNT_ZERO_OR_NEGATIVE`.
- `description.trim().length > 0` иначе `INVALID_EXPENSE_DESCRIPTION`.
- `payerId` существует, иначе `PAYER_NOT_FOUND`.
- `splitAmong.length >= 1`, все существуют, уникальны, иначе `INVALID_SPLIT_AMONG`.
- Плательщик может отсутствовать в `splitAmong` — допустимо.

### 4.4 Удаление расхода

```
function deleteExpense(state: ApplicationState, expenseId: UUID):
  { state: ApplicationState } | LogicError
```

Правила:
- Если расход не найден — `EXPENSE_NOT_FOUND`.

### 4.5 Расчёт балансов

```
function computeBalances(state: ApplicationState): Balance[]
```

Определения:
- Для каждой траты `Expense` рассчитываются доли каждого бенефициара (см. раздел 5 — денежные вычисления).
- Для участника: `paid_cents` — сумма `amountCents` всех расходов, где он `payerId`.
- `owed_cents` — сумма его долей по всем расходам, где он включён в `splitAmong`.
- `netCents = paid_cents − owed_cents`.
- Инвариант: сумма `netCents` по всем участникам равна 0.

### 4.6 Расчёт рекомендуемых переводов

```
function computeSettlements(balances: Balance[]): Transfer[]
```

Правила и алгоритм — см. раздел 6. Выход — детерминированно отсортированный список переводов.

### 4.7 Сохранение и загрузка состояния

```
function serialize(state: ApplicationState): string // JSON
function deserialize(payload: string): ApplicationState | LogicError
```

Правила:
- Сериализация — компактный JSON без лишних пробелов. Схема версии фиксируется в `schemaVersion`.
- Десериализация валидирует схему, типы, UUID-форматы, неотрицательность сумм, уникальность id. При отклонении — ошибки `STATE_*` (см. 7.3).

## 5. Правила денежных вычислений и распределений

Единица хранения — копейки (`amountCents` — целое число). Деление всегда целочисленное с компенсацией остатка без потери копеек.

Распределение `Expense.amountCents` между `N` бенефициарами:
1. `base = floor(amountCents / N)`.
2. `remainder = amountCents % N`.
3. Отсортировать `splitAmong` по возрастанию `UUID` (лексикографически).
4. Первым `remainder` участникам выдать `base + 1`, остальным `base`.

Инварианты:
- Сумма долей равна `amountCents`.
- Никакие доли не отрицательны.
- Плательщик обязан платить свою долю только если он входит в `splitAmong`.

Особые случаи:
- `N = 1` — весь `amountCents` на одного участника.
- Плательщик вне `splitAmong`: он кредитует остальных на полную сумму.

## 6. Алгоритм взаимозачёта (Transfers)

Цель: предложить детерминированный набор переводов без излишних транзакций, но без обещания глобального оптимума.

Подготовка:
- Сформировать списки: `creditors = [{id, credit=netCents>0}]`, `debtors = [{id, debt=−netCents>0}]`.
- Отсортировать `creditors` и `debtors` по `id` (лексикографически). Это обеспечивает детерминизм независимо от отображаемых имён.

Жадный алгоритм:
1. Идти по `debtors` в порядке сортировки.
2. Для текущего должника последовательно закрывать долг первыми доступными кредиторами в их порядке.
3. На каждом шаге формировать перевод `min(debt, credit)`; уменьшать соответствующие величины; при нуле — переход к следующему кредитору/должнику.

Свойства:
- Количество переводов ограничено `(#участников с net != 0) − 1` в типичных случаях жадного алгоритма.
- Детализация переводов детерминирована выбором порядка.
- Сумма всех переводов по участнику совпадает с его `|netCents|`.

## 7. Бизнес-ограничения и ошибки

7.1 Валидация входов
- Нулевая или отрицательная сумма расхода запрещена.
- Отсутствующий плательщик запрещён.
- Пустой список бенефициаров запрещён.
- Дублирование идентификаторов в импортируемом состоянии запрещено.
- Плательщик может быть не в списке бенефициаров — разрешено.

7.2 Операции над участниками
- Удаление участника, фигурирующего в истории, запрещено (`PARTICIPANT_IN_USE`).
- Разрешён soft-hide через `archived` (поведение UI — предмет согласования).

7.3 Коды ошибок (устойчивая форма)
- `INVALID_PARTICIPANT_NAME`
- `PARTICIPANT_NOT_FOUND`
- `PARTICIPANT_IN_USE`
- `PAYER_NOT_FOUND`
- `INVALID_EXPENSE_DESCRIPTION`
- `INVALID_AMOUNT_ZERO_OR_NEGATIVE`
- `INVALID_SPLIT_AMONG`
- `EXPENSE_NOT_FOUND`
- `DUPLICATE_PARTICIPANT_ID`
- `DUPLICATE_EXPENSE_ID`
- `INVALID_ID_FORMAT`
- `STATE_SCHEMA_VERSION_UNSUPPORTED`
- `STATE_DATA_CORRUPTED`

Каждый `LogicError` должен содержать `message` и, при уместности, `details` (например, какие id отсутствуют/дублируются).

## 8. Инварианты состояния
- Все `Participant.id` уникальны; все `Expense.id` уникальны.
- Все ссылки `payerId` и `splitAmong` валидны.
- Сумма `Balance.netCents` по всем участникам равна нулю.
- Все `amountCents` и вычисленные доли — неотрицательные целые.
- Детализация долей каждого расхода суммируется точно в `amountCents`.

## 9. Примеры расчётов (детализированные)

Пример 1 — базовое равное деление:
- Участники: A(id=a), B(id=b), C(id=c).
- Расход: A платит 300₽ (30000 коп.), `splitAmong=[a,b,c]`.
- Деление: N=3 → base=10000, remainder=0 → каждому по 10000.
- Балансы: A `paid=30000`, `owed=10000`, `net=+20000`; B `net=−10000`; C `net=−10000`.
- Переводы: B→A 10000, C→A 10000.

Пример 2 — плательщик вне бенефициаров и остатки:
- Участники: A(id=a), B(id=b), C(id=c).
- Расход: B платит 100₽ (10000 коп.), `splitAmong=[a,c]`.
- Деление: N=2 → base=5000, remainder=0 → A=5000, C=5000.
- Балансы: B `paid=10000`, `owed=0`, `net=+10000`; A `net=−5000`; C `net=−5000`.
- Переводы: A→B 5000, C→B 5000.

Пример 3 — остаток распределяется детерминированно:
- Участники: A(id=1), B(id=2), C(id=3).
- Расход: C платит 10₽ (1000 коп.), `splitAmong=[1,2,3]`.
- Деление: base=floor(1000/3)=333, remainder=1 → сортировка id: ["1","2","3"], первый получает +1.
- Доли: id=1 → 334, id=2 → 333, id=3 → 333.
- Балансы: C `paid=1000`, `owed=333`, `net=+667`; A `net=−334`; B `net=−333`.
- Переводы (sorted ids): A→C 334, B→C 333.

Пример 4 — несколько расходов:
- Участники: A(id=a), B(id=b), C(id=c), D(id=d).
- Расход 1: A платит 400₽, split=[a,b,c,d] → каждому 100₽.
- Расход 2: D платит 150₽, split=[b,c] → каждому 75₽.
- Итоговые `net`:
  - A: paid=400, owed=100 → +300
  - B: paid=0,   owed=175 → −175
  - C: paid=0,   owed=175 → −175
  - D: paid=150, owed=100 → +50
- Переводы (копейки): B→A 100, B→A 75? Нет, жадный порядок по id: b сначала платит A до исчерпания его кредита +300 → B→A 175, C→A 125, затем C→D 50.

Проверка: суммы по каждому участнику соответствуют `|net|`.

## 10. Требования к тестированию

Юнит-тесты:
- Распределение суммы на N человек с остатком, проверка инварианта суммы и детерминированности назначения лишних копеек.
- Плательщик вне `splitAmong` — проверка балансов и переводов.
- Несколько расходов — проверка агрегации `paid`/`owed` и суммы `net`.
- Алгоритм взаимозачёта — детерминированный выход и отсутствие избыточных мелких переводов в базовых кейсах.

Инварианты:
- Сумма `netCents` = 0.
- Неотрицательность долей и сумм.
- Устойчивое поведение при перестановке входов (детерминизм за счёт сортировки по id).

Граничные сценарии:
- Сумма 1 коп., 2 участника → один получает 1, другой 0.
- Большие суммы (до безопасного диапазона 53-битного целого JS) — отсутствие переполнения; рекомендовано ограничение `amountCents <= 9e15` (см. вопросы к UI).
- Пустой список бенефициаров — ошибка.
- Отсутствующий плательщик — ошибка.
- Дублирование id в импортируемом состоянии — ошибка.

Примеры Given/When/Then (сокращённо):
- Given: A,B; When: addExpense(100, payer=A, split=[A,B]); Then: balances: A=+50, B=−50, transfers: B→A 50.
- Given: A,B,C; When: 10₽, payer=C, split=[A,B,C]; Then: A owes 334, B owes 333, C credit 667, transfers: A→C 334, B→C 333.
- Given: participant used in expenses; When: removeParticipant; Then: error `PARTICIPANT_IN_USE`.

## 11. Допущения и совместимость

- Имя участника не уникально (пока). Уникальность может реализовываться UI.
- Идентификаторы стабильны, генерируются UUID v4, сохраняются и не переиспользуются.
- Порядок сортировки для детерминизма — лексикографический по UUID.
- Weighted-распределения не поддерживаются в v1; расширение возможно в v2 (см. вопросы).

## 12. Формат сериализации и восстановление

- JSON со структурой `ApplicationState`.
- При чтении выполняется строгая валидация: типы, обязательные поля, уникальность id, ссылки, значения > 0.
- При несоответствии — `STATE_DATA_CORRUPTED` или `STATE_SCHEMA_VERSION_UNSUPPORTED`.

## 13. Нефункциональные критерии приёмки (logic)

- Детерминизм: одинаковые входы → одинаковые выходы (балансы, переводы).
- Отсутствие потери копеек: сумма долей = сумма расходов, сумма `net` = 0.
- Ошибки имеют стабильные коды; сообщения не зависят от среды и могут локализоваться.
- Операции не изменяют состояние при ошибке (atomicity на уровне функции: либо полностью применённое новое состояние, либо исходное).
